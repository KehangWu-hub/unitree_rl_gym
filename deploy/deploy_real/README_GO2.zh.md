# Go2真机部署

本入口复用Isaac Gym导出的45维Actor、`deploy.yaml`和公共策略接口。代码虽已包含安全检查，实体机器人仍可能造成设备损坏或人身伤害；必须按下列阶段逐级验证，禁止直接落地启动策略。

策略程序的键盘速度输入目前仅用于DDS仿真与只读影子检查。实体趴卧阻尼及第二终端停止请求已检查，电脑断电或网线断开后的停机行为尚未确认；`deploy_real_go2.py`在真机网卡上仅允许`--read-only`。直接运行`python deploy/deploy_real/deploy_real_go2.py eno1`会在初始化DDS前报错。真机受限电机验收与限时策略试跑使用下方独立的`go2_commission`入口。

宇树手机App可以操作原厂运动功能；只读检查期间可保留原厂控制。本程序尚未读取App虚拟摇杆作为策略速度指令。底层电机控制通常需要退出原厂运动服务，因此App的停止按钮不能未经验证就作为底层策略的停机方式。

## 控制状态

- `Passive`：程序启动状态；单独运行`--read-only`时保持此状态，只记录数据。
- `FixStand`：运行`--shadow-policy`或`--simulation-auto`后自动进入。前者只计算5秒插值目标；后者在仿真中下发目标。
- `Policy`：上述5秒插值完成且安全检查通过后，程序自动进入策略计算；影子模式不下发，DDS仿真模式下发。
- `MotorTest`：仅使用`--motor-test`进入；从当前关节角开始做单关节小幅往返，不运行策略。
- `Damping`：发生通信、姿态、关节、动作或力矩异常，或退出仿真程序时进入。只读模式下仅在程序内部记录状态，不发送电机命令。

键盘`W/S`、`A/D`、`Q/E`分别给出前后、侧向和转向速度；当前上限分别为0.5米/秒、0.3米/秒和0.5弧度/秒。

## 只检查模型，不启动DDS

```bash
conda activate unitree-rl
python deploy/deploy_real/deploy_real_go2.py --check
```

该命令必须先通过。它不会连接仿真器或机器人，也不会创建LowCmd发布器。

## 真机只读与策略影子检查

在机器人使用原有控制方式保持稳定时，连接有线网卡 `eno1`，先运行：

```bash
conda activate unitree-rl
python deploy/deploy_real/deploy_real_go2.py eno1 --read-only
```

该模式不创建LowCmd发布器。保持机器人静止，观察约10秒后按终端`Ctrl+C`结束；不要为测试本程序而触发原厂运动操作。然后运行：

```bash
python deploy/deploy_real/deploy_real_go2.py eno1 --read-only --shadow-policy --duration 12
```

该命令自动在程序内部经历5秒虚拟`FixStand`，随后以零速度指令计算约7秒策略目标，不向机器人发送电机命令。检查新生成的`logs/go2_real/*.jsonl`中出现`policy`记录，且`reason`为空、目标角均为有限值。若未进入`policy`或有安全故障，先检查输入和日志。

只读阶段不要关闭机器人原有的运动服务；它仍负责保持机器人姿态。

## 键盘输入预演（不连接真机电机）

在官方DDS/MuJoCo仿真启动后，可在前台交互式终端运行：

```bash
python deploy/deploy_real/deploy_real_go2.py lo \
  --domain-id 1 --simulation-auto --keyboard --duration 20
```

程序先执行5秒虚拟站立，再进入策略。`W/S`前后、`A/D`左右、`Q/E`转向；`X`或空格把速度目标归零，策略继续运行并保持站立。每次方向按键只维持0.25秒，未持续收到按键时自动归零；终端无法可靠报告松键事件，因此按键重复间隔会影响连续运动。`Z`或`Ctrl+C`退出并发送约1秒阻尼命令；仿真中的机器人随后会降低机身，不能把它当作保持站立的停车方式。

2026-09-29的动态DDS/MuJoCo测试已验证两次键盘前进、`X`归零和空格归零：策略运行359帧，软件安全故障为零；停止行走期间机身高度约0.32米。`Z`退出后仿真机器人降低机身。该结果只适用于所用MuJoCo模型和测试指令，不代表真机停机已验收。

下次真机开机时，可在只读影子模式下检查键盘输入是否进入策略日志：

```bash
python deploy/deploy_real/deploy_real_go2.py eno1 \
  --read-only --shadow-policy --keyboard --duration 20
```

这个模式不会创建LowCmd发布器。键盘的`X`、空格和超时归零只是速度目标变化，不能充当真实电机急停。真机主动控制的启动检查仍会阻止`--keyboard`绕过只读限制。

## DDS仿真验证

先在独立终端启动官方 `unitree_mujoco`，机器人选择Go2，DDS domain使用1，网卡使用本地回环 `lo`。随后运行：

```bash
conda activate unitree-rl
python deploy/deploy_real/deploy_real_go2.py lo \
  --domain-id 1 --simulation-auto --duration 12 \
  --command 0.3 0.0 0.0
```

必须在DDS仿真中检查状态机、键盘速度与归零、关节映射、CRC、控制周期、停止与异常阻尼，不允许跳过此阶段连接真机。

## 独立停止与受限电机测试

主动DDS仿真现在由独立看门狗进程作为唯一LowCmd发布者。主程序只读取状态、计算目标并发送给看门狗。看门狗独立检查状态、目标角、增益和估算力矩；控制命令超过100毫秒未更新时，即使主程序卡住或被`SIGKILL`结束，也会锁存停止、将Kp归零并持续发送约1秒阻尼。停止后必须重新启动程序才能再次主动控制。

在另一个终端停止domain 1的仿真控制：

```bash
conda activate unitree-rl
python -m deploy.deploy_real.go2_watchdog --stop --domain-id 1
```

命令收到看门狗确认后才输出成功；确认表示阻尼指令已发送，不代表机器人保持站立。该路径仍依赖同一台电脑、看门狗进程和DDS通信，不能覆盖电脑断电、看门狗被强制结束或网络完全中断，也没有验证实体Go2的响应。

已有Go2 DDS仿真运行在`lo`、domain 1时，可以运行受限测试：

```bash
python deploy/deploy_real/deploy_real_go2.py lo --domain-id 1 \
  --motor-test --test-joint FL_hip_joint --test-amplitude 0.01 --duration 2
```

这条命令本身不启动MuJoCo。它以当前关节角为起点，只改变所选关节的目标；其余关节以低增益保持采样时的姿态。默认目标偏移0.01弧度（约0.57度），可设置的最大绝对偏移为0.02弧度，时长1至3秒；使用平滑往返曲线，Kp=5、Kd=0.5。主动测试期间，实际关节位移超过0.04弧度、关节速度超过2弧度/秒、估算PD力矩超过1牛米或出现其他安全异常时进入阻尼。目标位移限制不能保证实际位移或跌倒风险；这些参数尚未通过真机验收。

可直接运行自动验收，无需机器人或额外仿真程序：

```bash
GO2_DDS_TESTS=1 python -m unittest discover -s tests -p test_go2_watchdog.py -v
```

测试使用本项目Go2 MJCF资产和官方SDK消息，自动启动无窗口的MuJoCo/DDS测试桥接，覆盖单关节往返、地面偏移超限、第二终端停止、主程序冻结、主程序强制结束和LowState断流。单关节方向检查采用固定机身、零重力条件；地面场景单独保留重力，验证低增益导致偏移超限时会停止。这些测试不证明无支撑真机测试可行。

## 真机分阶段验收

1. 完成上面的只读与策略影子检查，逐项核对实体IMU、关节顺序、App虚拟摇杆的数据来源和状态更新频率。
2. 原有受限电机测试与看门狗已完成仿真验证，仍限定`lo`与非零domain。实体趴卧验收使用下节新入口；常规键盘策略入口继续限制为只读；限时真机策略使用下节独立入口。
3. 先在机身已趴在地面时验收阻尼、第二终端停止及原厂模式恢复，再测试单个髋关节。地面仿真中低增益无法保证承重站立，不得站立时执行本节真机低增益验收。
4. 受限电机控制与急停在真机通过后，再逐步测试站立、停止、微速移动及策略；任一步异常都停止并检查日志。

DDS仿真停机时由看门狗持续发送约1秒阻尼命令；真机只读模式始终不发送电机命令。主程序的计算记录保存在 `logs/go2_real/*.jsonl`；实际发布命令的记录位于 `logs/go2_real/watchdog/*.jsonl`，包含IMU、关节状态、目标角、增益、控制状态和停止原因。

## 首次趴卧真机验收

2026-10-09已检查实体趴卧零Kp阻尼、第二终端停止请求及原厂模式恢复。现场确认恢复normal会自动站起，随后使用者通过App卧倒；这不是自定义策略站起。左前髋0.005弧度测试无安全故障，但实际角度变化接近静止波动，现场也无明显动作；该次未确认角度响应和实体方向；后续12关节与整机接管结果见下方进度表。详细结果见[工作日志](../../.codex/Doc.md#2026-10-09-实体左前髋小幅测试响应与方向尚未确认)。

先在电脑上检查，不需要机器人：

```bash
python -m deploy.deploy_real.go2_commission --check
```

以下命令会改变原厂运动模式并发送电机指令。开机后先用App卧倒，现场确认机身趴在平坦防滑地面、周围无人、手不接触关节，保持摇杆居中。`--confirm-prone`是现场确认；关节角和IMU检查不能证明机身实际接触地面。不要先用App站起。

先准备第二个终端，在需要停止时执行：

```bash
python -m deploy.deploy_real.go2_watchdog --stop --domain-id 0
```

首次仅验收阻尼，在前台终端执行：

```bash
python -m deploy.deploy_real.go2_commission eno1 \
  --damping-test --confirm-prone --release-mode --duration 2
```

程序持续检查一秒趴卧与静止状态，再查询原厂模式。只接受`normal`或已释放的空模式；退出原厂模式成功并确认后，检测其他LowCmd发布者，才创建发布器。未收到启动请求前不发送电机指令。测试中所有Kp=0、Kd=0.5；到期或停止后Kp=0、Kd=3持续约一秒。当前终端的`X`、空格、`Z`及`Ctrl+C`均结束本次测试，不是速度归零后继续运行。

第二终端停止确认表示独立进程已锁存停止并将阻尼指令提交DDS，不代表电机实际停止。主终端心跳超过100毫秒未更新也会停止；仍依赖电脑、验收进程和网线。App按钮在原厂模式退出后是否有效尚未验收，不作为这个入口的停止路径。

测试结束后不自动恢复原厂模式。恢复normal可能立即触发原厂站起，不能保证恢复后保持趴卧。确认验收进程已退出、机身仍趴卧、周围无人，先在App准备好卧倒按钮，再显式恢复：

```bash
python -m deploy.deploy_real.go2_commission eno1 \
  --restore-normal --confirm-prone --allow-factory-stand
```

恢复命令会检查新鲜且CRC正确的趴卧状态、停止接口不存在、当前模式为`normal`或空，再请求并确认`normal`。这些是恢复前的检查，不能约束原厂恢复后的站起动作。原厂站起后由使用者用App卧倒并现场确认；本程序不发送原厂卧倒指令。模式确认不能替代App实际控制与姿态检查。也可以保持当前趴下状态直接关机。退出原厂模式后若启动检查失败，也可能需要这条恢复命令；不要直接尝试启动策略。

阻尼、第二终端停止、原厂恢复都在实体通过后，才执行单髋关节测试：

```bash
python -m deploy.deploy_real.go2_commission eno1 \
  --motor-test --confirm-prone --release-mode \
  --test-joint FL_hip_joint --test-amplitude 0.005 --duration 2
```

默认偏移0.005弧度（约0.29度），最大绝对偏移0.01弧度，时长1至3秒。只允许四个髋关节；所选髋关节Kp=5，其余11个关节Kp=0，测试期间所有Kd=0.5。主动髋关节目标仍执行原有策略关节限位；趴卧小腿仅读取，不施加位置增益，也不修改策略限位。记录位于`logs/go2_real/commission/`。

验收入口默认目标发布频率500Hz，与官方低层示例的2毫秒周期一致；Python实际调度频率需要从日志测量，不能保证达到500Hz。`--publish-hz 50`保留为频率对照。策略程序仍按50Hz计算，常规键盘策略入口仍禁止真机下发；仅独立限时试跑已下发。反馈日志增加`feedback`：实时`tau_est`、电机mode/lost/温度、状态tick和独立订阅的LowCmd回显/CRC。`tau_est`是估算量，DDS回显与mode数值都不能单独证明电机已执行命令。

趴卧验收范围来自2026-10-09的实际状态：髋关节±0.5、大腿1.1至1.6、小腿-2.9至-2.6弧度，横滚/俯仰不超过0.2弧度。这是本次姿态匹配条件，不是机械运动范围或站起轨迹。初始关节速度不超过0.2弧度/秒；测试中任一关节相对起点偏移超过0.04弧度、速度超过2弧度/秒、估算PD力矩超过1Nm、CRC持续错误导致状态超时或心跳超时都会锁存阻尼。极小目标偏移仍不能保证实际动作无风险。

阻尼和逐关节模式不站起、不运行策略。下节的`--stand-check`是独立选择的整机站立流程，仍无行走或策略功能。退出后的姿态以及App恢复需现场核对，软件检查通过不等于真机验收完成。

## 单次响应诊断方案

2026-10-09已首次执行完整实体方案，结果为`force_response_only`：正负力矩反馈达到判据，编码器响应未达到判据；无安全故障，使用者确认无异常，结束后normal与App恢复并已卧倒。后续复测应先核对工作日志中的限制，不能依据这一结果直接运行策略。

此前0.005弧度、Kp=5的单向测试力矩太小，结果不足以辨认实际响应。本方案固定3秒、幅度0.005弧度、仅所选髋关节Kp=20，其余关节Kp=0、所有Kd=0.5；测试依次为0.4秒基线、0.8秒正向平滑往返、0.4秒基线、0.8秒负向平滑往返、0.6秒基线。目标对应弹簧项峰值约0.1Nm，实际PD估算与反馈另行检查。已有一次实体力矩响应记录，尚未确认角度响应，不代表保证安全或保证响应。

现场仍需确认趴卧、停止终端就绪、没有人接触关节。准备完成后使用：

```bash
python -m deploy.deploy_real.go2_commission eno1 \
  --response-test --confirm-prone --release-mode
```

本方案固定参数，不自动增加幅度或增益。额外锁存阻尼条件：任一关节相对起点位移超过0.01弧度、速度超过0.5弧度/秒；估算PD力矩超过0.2Nm；所选髋反馈估算力矩绝对值超过0.5Nm；力矩反馈缺失或非有限。原有通信、心跳、姿态与停止检查保留。结束后的原厂恢复仍可能自动站起，需按上一节协调；也可保持趴卧关机。

离线分析日志，不连接机器人：

```bash
python -m deploy.deploy_real.go2_commission --analyze <本次JSONL日志>
```

判定要求有效测试记录至少跨越2.8秒、至少100个不同state tick、完整基线和正负峰值窗口各至少20帧，以及有效DDS回显。比较正负峰值与基线中位数：

| 项目 | 判据 | 能确认的范围 |
| --- | --- | --- |
| 力矩反馈响应 | 正负变化分别越过±max(0.05Nm, 3倍基线稳健噪声) | 估算力矩与目标存在方向一致的反馈变化，不能作为精确实测力矩 |
| 编码器响应 | 正负变化分别越过±max(0.001rad, 4倍基线角度跨度) | 该SDK索引的角度有方向一致的变化 |
| 实体关节映射/方向 | 另需现场观察和官方映射核对 | 自动报告始终不将其标为已确认 |

结果分为`force_and_encoder_response`、`force_response_only`、`encoder_response_only`、`inconclusive`与`aborted`。力矩有响应而角度无响应只能提示存在负载等候选原因，不能直接断言摩擦；两个信号都无响应时仍无法分清激励不足和指令未执行。数据不足或安全故障均不能升级到策略控制。脚本不会依据判定自动启动策略。

## 逐关节响应验收

`--joint-check`固定3秒、目标幅度0.02弧度（约1.15°）、仅所选关节Kp=40，其余Kp=0，所有Kd=0.5。目标弹簧项峰值约0.8Nm；这不是实际运动幅度或力矩的保证。软件检查与本机DDS检查已经通过。12关节均已采集且估算力矩响应通过；9关节通过本轮角度判据，右前髋及两个前小腿角度响应不足，未改判据或自动增加参数。

```bash
python -m deploy.deploy_real.go2_commission eno1 \
  --joint-check --confirm-prone --release-mode --test-joint FL_hip_joint
```
